# Precomputed analogue discovery

The discovery workflow reads a local SQLite index at runtime. It does not fetch or process elevation data on selection. For a compact demonstration, omit the NASADEM command below: the checked-in compact terrain windows include Aeolis on Mars, Shackleton on the Moon, and Earth candidates. Run the NASADEM command to expand the Earth index from the locally available source archives:

```sh
uv sync --locked --extra dev
uv run python -m scripts.build_nasadem_contexts
uv run python scripts/build_feature_index.py
uv run uvicorn twinworld.api:app --reload
cd apps/twinworld
npm ci
npm run dev
```

Open http://127.0.0.1:5173. Indexed terrain markers identify actual precomputed raster windows; clicking a marker or a covered surface point starts a comparison. Points outside those windows do not resolve to a distant site. The database and generated NASADEM rasters are kept in ignored `artifacts/discovery/`. Set `ENOM_DISCOVERY_INDEX` to select another index file before starting the API.

The NASADEM builder processes the locally available `data/earthdata-scraper/nasadem/NASADEM_HGT_*.zip` archives with a deterministic 9×9 set of centres per tile. It uses the existing NASADEM adapter's HGT/NUM/SWB reader, masks voids, water and zero NUM values, and reprojects each 22×22 window to approximately 463 m posting. Output metadata includes the archive SHA-256, source DOI, processing description, valid fraction and six terrain measurements. Only five are used for ranking. These tiles cover selected Australian locations, not a global representative sample. Adjacent windows can overlap and are not independent observations; the full ranking is retained and the displayed recommendations apply a geographic spacing rule. Validity of resampled pixels is not a measurement uncertainty estimate.

For optional broader coverage, `uv run python -m scripts.build_copernicus_contexts` requests bounded Copernicus GLO-30 windows in a 3×3 arrangement around existing Earth pilot regions. This step requires network access to Microsoft Planetary Computer and can take several minutes; it does not download a global raster. Each attempted window is reported and a manifest records failures. Run the index builder again to incorporate successful contexts. Provider data and remote access can change, so the resulting release is a locally reproducible snapshot once generated rather than a guarantee of identical future downloads. Signed asset URLs are not stored in the index.

For a broad, equal-area Earth sample, run `uv run python -m scripts.build_global_earth_contexts --target-count 1000 --candidate-count 20000`. The sampler generates deterministic Fibonacci-sphere candidates, keeps centers on the Natural Earth 1:110m land mask ([Natural Earth downloads](https://www.naturalearthdata.com/downloads/)), checks the Copernicus GLO-90 tile catalogue ([AWS Open Data Registry](https://registry.opendata.aws/copernicus-dem/)), and enforces 100 km minimum center spacing. It reads only the needed source COG ranges through a local metering proxy, which rejects unbounded GET requests and upstream responses that ignore byte ranges. It retains a compact 22×22 metric DEM window and a 102×102 modal summary from [ESA WorldCover 2021 v200](https://esa-worldcover.org/en/data-access) per successful context; it does not save source tiles. A per-output lock prevents concurrent acquisition runs. Progress, rejected candidates, response-body bytes, geographic bins, generated storage, and peak staging storage are written to `artifacts/discovery/earth-glo90/manifest.json`. The manifest is resumable and tied to the sampling grid, source catalogue checksums and seed. `--max-source-bytes` defaults to 4 GB and `--max-storage-bytes` to 5 GB; the source byte limit can be exceeded by at most the final completed context's reads because the pipeline stops before the next candidate. The report separates summed context footprint area from WorldCover-mapped non-water area; neither is continuous global land coverage. Natural Earth filtering is coarse and the sample does not guarantee representation of every landform or biome. Rebuild the SQLite index afterward with `uv run python scripts/build_feature_index.py`; the builder reports elapsed time, prevents concurrent publication, validates the SQLite database, and atomically replaces the prior index only after validation.

The index builder also scans local Copernicus, MOLA and LOLA sidecars under `data/terrain/`. Missing raster files are listed as skipped; a fresh checkout may contain fewer source windows than a development checkout. The compact source-backed Aeolis MOLA terrain window and its paired count mask are included for the Mars demonstration; the Shackleton polar window is included for the Moon demonstration. Build/reacquire missing source windows with the ingestion scripts described in `REPRODUCIBILITY.md`. The SQLite schema version 4 stores context metadata and original raster CRS/transforms in `contexts`, explicit place associations in `places` and `context_places`, evidence support in `context_quality`, scientific measurements in `measurements`, source identifiers in `source_products`, and conservative geographic bounds in `bounds` and its R*Tree. It records input elevation and paired count-raster SHA-256 checksums and the builder checksum. For MOLA, the elevation and count rasters must have identical grids and the elevation valid-data mask must exactly match positive observation counts; otherwise the context is excluded. The count-grid support must also agree with the sidecar. Global GLO-90 contexts enter the index only through the completed-context list in the acquisition manifest. Their WorldCover class fractions are retained as usable metadata only when the product identity, mapped fraction, sample count, class groups, and fraction sum are internally consistent; malformed summaries are marked unavailable so they cannot satisfy a land-cover filter. The release identity changes when a raster or the builder changes. A coordinate is rechecked against the projected raster rectangle; the original click and the analysis footprint are distinct. Moon click coordinates are interpreted in the LOLA mean-Earth/polar-axis frame; alignment with the displayed basemap has not been independently verified.

`GET /api/discovery/index` reports the release hash, evidence policy and coverage counts. `GET /api/discovery/coverage?body=mars` lists contexts, their boundaries, and whether each has at least one compatible Earth comparison under the default five-feature search. The eligibility flag is not a claim of full evidence, and changing weights can make a context unrankable. `POST /api/discovery/resolve` accepts `body`, `latitude_deg`, and `longitude_east_deg`. `POST /api/discovery/rank` accepts the returned `index_id`, a `context_id`, all five terrain-feature `weights`, optional eight-dimension `dimension_weights`, class bounds in `land_cover_min_fractions` and `land_cover_max_fractions`, and `result_limit`/`result_offset` pagination. Omitting dimension weights selects terrain only. Ranking covers the full eligible corpus; paged `results` preserve deterministic order, while the response also returns the total count, near-equivalent count and a separately diversified top-10 recommendation list. Full indexed context details are available from `GET /api/discovery/contexts/{context_id}`. The rules are configured and versioned in `configs/discovery-policy.json`.

Comparisons use the existing scorecard's exponential component scores and unit/scale compatibility checks. Footprint side lengths are sorted before comparison, so a 90-degree raster rotation does not change compatibility; corresponding side lengths and total footprint area must each fall within the configured ratio. This is an axis-aligned rectangle approximation from geodesic distances between edge midpoints, not a full polygon overlap test. The versioned ranking policy uses a 0.01 absolute score tolerance to flag near-equivalent candidates with the same evidence tier and matched-feature count; ties remain deterministically ordered by score and context ID. Geographic diversification is applied after scoring, and the full result set remains available. The available corpus remains geographically uneven. The Moon polar LDEC product reports native shot support, whereas the cylindrical LOLA product does not; grid validity must not be read as direct observation support.

MOLA's range is calculated from bins with positive observation counts. The versioned policy requires at least 25% observed bins for a range-only exploratory ranking, and such a result is always `limited_evidence`; the sampled range can miss unsampled extremes and is not a complete-footprint estimate. The included Aeolis window has 153 of 484 bins observed (31.6%), so it can retrieve elevation-range matches when a footprint-compatible Earth context is indexed. PDS describes MEGDR products as binned altimetry maps paired with a per-cell observation-count map ([PDS MOLA MEGDR documentation](https://pds-geosciences.wustl.edu/missions/mgs/megdr.html)).

Global Earth contexts include ESA WorldCover 2021 v200 summaries. Each proportion is the frequency of a class among modal classes in a 102×102 grid of approximately 100 m cells, not a field survey or a 10 m independent measurement. Optional minimum and maximum share filters are supplied per request and have no default exclusions. If a filter is active, candidates with partial or unavailable classification are ineligible; missing classes are never treated as zero. The response distinguishes missing classifications from classifications that fail the requested bounds. Copernicus GLO-90 is a digital surface model and may include vegetation and structures. NASADEM and Copernicus are different source products; their systematic differences are not corrected. Similarity is a ranking index, not a probability, a validated analogue, or an assessment of mission suitability.

## Browser regression tests

After building the index and installing the application dependencies, install Playwright's browser and run the tests:

```sh
cd apps/twinworld
npx playwright install chromium
npm test
```

The tests start the local API and frontend when they are not already running. They exercise desktop and mobile Mars discovery, missing evidence after changing weights, an out-of-coverage surface click, and an out-of-order response after changing bodies. An installed Chrome executable can be selected with `ENOM_BROWSER_PATH` when needed. A sandbox that prevents browser process launch may require running these tests in a normal host terminal.

## Local benchmark

With a built index, run `uv run python scripts/benchmark_discovery.py --samples 20` to report warm lookup, exact ranking, local TestClient response timings, response size and index identity. Browser tests print selection-to-result and selection-to-camera-focus elapsed times; these are individual observed runs, not percentile claims. They include rendering and local network traffic, and vary with hardware and browser load.

Ranking responses include the complete near-equivalent count but return at most 100 corresponding context IDs. `near_equivalent_ids_truncated` indicates when additional IDs exist; the paginated ranking remains available for inspection. This bounds response growth when many candidates tie.

Results are ordered first by the number of independent evidence groups that contribute at positive weight, then by the partial similarity index, evidence completeness and stable context ID. Terrain and its operations proxy share one group. This prioritizes broader available evidence without assigning a score to missing measurements. The order is a research policy, not a validated analogue relevance model; scores are most directly comparable within the same evidence tier.
